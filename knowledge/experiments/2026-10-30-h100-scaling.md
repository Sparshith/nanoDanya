# H100 data-parallel scaling, 2026-10-30

**Eight H100s deliver 4.06x steady-state speedup at global batch 64, using 1.97x the GPU-hours for the same updates.** Four H100s deliver 2.70x speedup at 1.48x GPU-hours. Single-source DDP is implemented in the recipe trainer. Distillation and RL are unchanged.

## Method

Human-only coverage data (`datasets/games/15m`), L16/1024 GPT (231,534,592 parameters), context 512, global batch 64. Identical seeded global batch order at every GPU count. Each worker builds the same global batch and trains only on its disjoint slice. Valid-target counts remain global, including fully padded slices.

Modal minusx workspace, profile `second`; strict H100 80GB requests, PyTorch 2.5.1+cu124, BF16 computation and FP32 loss, AdamW, compiled model plus loss. Every container reserves 32 physical CPU cores and 64 GiB host memory; the timing loop uses two Torch CPU threads per worker. Twenty warmup updates precede three timed blocks of 200 updates. Timing includes sampling, transfers, forward/backward, gradient synchronization, clipping, and optimizer work. The timing loop uses fixed peak LR across all counts and is not a learning-quality comparison. Production training retains its recipe schedule.

Step timings exclude compilation, validation, and checkpointing. Observed startup/warmup was 365.6, 262.7, 269.7, and 578.2 seconds for 1/2/4/8 GPUs. These are not controlled cold-cache comparisons: caches were reused during debugging. The four-GPU samples vary by about 6%; avoid interpreting small differences as decisive.

## Operational check

Twenty real scheduled updates, initial/final validation, checkpoint writes to the Modal Volume, and actual Volume commits were also measured with existing compiler caches. Temporary checkpoints were removed afterward.

| H100s | Training segment, seconds | Container execution, seconds | Estimated compute cost |
|---:|---:|---:|---:|
| 1 | 97.37 | 109.49 | $0.18 |
| 8 | 93.53 | 117.28 | $1.10 |

Both runs trained on exactly 592,817 supervised targets. Final held-out CE was 9.563568980 (1 GPU) and 9.563568914 (8 GPUs), a difference below 1e-7. The training-segment clock excludes process launch/process-group initialization and benchmark cleanup; the container clock includes that additional overhead. Neither short-run measurement supports an end-to-end speedup for tiny jobs. Multi-GPU benefits need enough updates to amortize startup and serial validation/checkpointing.

## Implementation and verification

- One worker per GPU, synchronized gradients, global token normalization, and accumulation without intermediate gradient synchronization.
- Exact source coverage and global batch size preserved. Validation, logs, checkpoint writes and Volume commit requests have one writer. Stop decisions are coordinated. Resume stores per-worker RNG and requires the same world size.
- CUDA DDP disables compiler graph partitioning (`torch._dynamo.config.optimize_ddp=False`). The initial partitioned eight-GPU attempt never reached timing within its budgeted window and reported pending NCCL work before CUDA graph capture. Keeping one compiled loss graph avoids interleaving per-bucket capture and collectives, at the cost of potential communication overlap. Final distributed timings all use this setting.
- 19 tests passed in the Linux Modal image, including raw gradient equality with unequal target counts and an empty worker slice, exact coverage, parameter updates, and exact CPU resume. Locally, 17 passed and the two Linux-only integration tests were skipped after macOS torchrun rendezvous failed.
- The actual eight-GPU trainer also completed the operational validation/checkpoint test. No full training run, Elo evaluation, larger-global-batch study, or long stress test was performed.
